# AMD Instinct MI250X

GPU architecture profile for the AMD Instinct MI250X accelerator.

## Detection Signals

This profile applies when the `type` label of `rocm_version_info` contains `MI250` (e.g., `"Aldebaran/MI200 [Instinct MI250X]"`). In the `omnistat-inspect` report card this surfaces as `overview.gpu_arch` containing `mi250x`.

## Peak Theoretical Performance (per OAM module, 2 GCDs)

| Data Type | Vector | Matrix |
|-----------|--------|--------|
| FP64 | 47.9 TFLOPS | 95.7 TFLOPS |
| FP32 | 47.9 TFLOPS | 95.7 TFLOPS |
| FP16 | — | 383 TFLOPS |
| BF16 | — | 383 TFLOPS |
| INT8 | — | 383 TOPS |
| INT4 | — | 383 TOPS |

Per GCD (one Omnistat "card"): divide by 2. TDP: 500W (560W peak). Memory bandwidth: 3.2 TB/s.

**Per-GCD peaks** (for %-of-peak from `hardware_counters` FLOPS, which are summed per GCD then rate-averaged across GCDs):

| Data Type | Vector (per GCD) | Matrix (per GCD) |
|-----------|------------------|------------------|
| FP64 | 24.0 TF/s | 47.9 TF/s |
| FP32 | 24.0 TF/s | 47.9 TF/s |
| FP16 | — | 191.5 TF/s |
| **BF16** | — | **191.5 TF/s** |

The **per-GCD BF16 matrix peak is 191.5 TF/s** — divide a job's per-GCD `active_rate_flops_per_s` for `bf16`/`matrix` by this to get %-of-peak.

## Multi-Die Architecture

The MI250X is a multi-chip module containing 2 Graphics Compute Dies (GCDs) per package. Each GCD appears as a separate GPU card in the system. A node with 4 MI250X packages has 8 GPU cards (cards 0-7).

Card-to-package mapping:
- Cards 0, 1 → Package 0
- Cards 2, 3 → Package 1
- Cards 4, 5 → Package 2
- Cards 6, 7 → Package 3

## Power Reporting

**Only even-numbered cards report power** (cards 0, 2, 4, 6). Odd-numbered cards (1, 3, 5, 7) report 0W via `rocm_average_socket_power_watts`. This is expected hardware behavior, not a data collection error — the even card reports the combined power for both GCDs in the package. `omnistat-inspect` filters the all-zero odd-card series out of the variance breakdowns (Power shows `n=256` rather than `512` in `by_gpu`).

## Thermal Limits

AMD does **not** publish fixed junction/throttle temperatures for the MI250X in its
public data sheets. The actual slowdown (throttle) and shutdown limits are programmed
in firmware and **vary by VBIOS/firmware revision and individual board**, so they are
not authoritative as hard-coded constants. Always read the real limits at runtime and
treat the device-reported values as authoritative for that specific node:

- `amd-smi static --limit` (per-sensor slowdown/shutdown thresholds)
- `rocm-smi --showtemp`
- the `temp*_crit` / `temp*_emergency` files under `/sys/class/drm/card*/device/hwmon/`

As a rough orientation (confirm against the device — do not rely on these numbers):
- Edge and hotspot (junction) slowdown/shutdown limits sit around the **~100 °C** range.
- The VRAM/HBM2e limit is **lower** than the compute-die limits, so memory is often the
  first sensor to reach its slowdown point.

Mapping to Omnistat metrics:
- `rocm_temperature_celsius` is the **edge** sensor.
- `rocm_temperature_memory_celsius` is the **VRAM/HBM2e** sensor.
- The hotspot/junction sensor (hotter than edge by design) is not separately exported by Omnistat.

Interpreting telemetry against the runtime-read limits:
- **Normal**: edge and VRAM comfortably below their respective slowdown limits.
- **Elevated**: sustained readings approaching the slowdown limit -- check airflow,
  adjacent nodes, ambient/inlet (or coolant) temperature. Note that most MI250X
  deployments (e.g. HPE Cray EX / Frontier) are direct liquid-cooled, so a hot card
  more often points to a coolant-loop or flow issue than to room air.
- **Throttling**: when a sensor reaches its firmware slowdown threshold the GPU reduces
  clocks (SCLK) to protect itself; correlate with a drop in `rocm_sclk_clock_mhz`.
- **Shutdown**: at the shutdown threshold the device powers off to prevent damage.

Beyond the absolute thresholds, flag cards running materially hotter than their peers —
a relative outlier is often the earliest sign of a cooling problem before any limit is reached.

## Memory (HBM2e)

- **Capacity**: 64 GB per GCD, 128 GB per MI250X package
- **MCLK**: Fixed at 1600 MHz (no dynamic memory clock scaling)
- **Bandwidth**: ~1.6 TB/s per GCD theoretical peak

## DVFS (Dynamic Voltage and Frequency Scaling)

MI250X GPUs dynamically adjust core clock speed (SCLK) based on workload:
- Active compute: clocks ramp to boost frequency
- Idle/low utilization: clocks reduce to save power

This means lower mean clocks and lower mean power are **consequences** of lower utilization, not independent problems (see "Consequence Chains" in the main SKILL.md).

## RAS Error Blocks

RAS error counters on MI250X are organized by hardware block:

| Block | Component | Notes |
|-------|-----------|-------|
| `umc` | Unified Memory Controller | HBM memory errors |
| `gfx` | Graphics/compute engine | Compute pipeline errors |
| `sdma` | System DMA engine | Data movement errors |
| `mmhub` | Memory hub | Memory controller hub |
| `pcie_bif` | PCIe interface | Host interconnect |
| `hdp` | Host data path | Host-GPU data path |
| `xgmi_wafl` | xGMI/WAFL interconnect | GPU-to-GPU (inter-GCD and inter-package) |

## Hardware Counters (rocprofiler-sdk)

Hardware counters are collected via rocprofiler-sdk. Values are cumulative session totals — use delta (last - first) to measure work done during a job.

| Counter | Description |
|---------|-------------|
| `FETCH_SIZE` | HBM read (KB) |
| `WRITE_SIZE` | HBM write (KB) |
| `SQ_INSTS_VALU_MFMA_MOPS_BF16` | Matrix (MFMA) operations, BF16 |
| `SQ_INSTS_VALU_MFMA_MOPS_F16` | Matrix (MFMA) operations, F16 |
| `SQ_INSTS_VALU_MFMA_MOPS_F32` | Matrix (MFMA) operations, F32 |
| `SQ_INSTS_VALU_MFMA_MOPS_F64` | Matrix (MFMA) operations, F64 |
| `SQ_INSTS_VALU_ADD_F16` | Vector add instructions, F16 |
| `SQ_INSTS_VALU_ADD_F32` | Vector add instructions, F32 |
| `SQ_INSTS_VALU_ADD_F64` | Vector add instructions, F64 |
| `SQ_INSTS_VALU_FMA_F16` | Vector fused multiply-add instructions, F16 |
| `SQ_INSTS_VALU_FMA_F32` | Vector fused multiply-add instructions, F32 |
| `SQ_INSTS_VALU_FMA_F64` | Vector fused multiply-add instructions, F64 |
| `SQ_INSTS_VALU_MUL_F16` | Vector multiply instructions, F16 |
| `SQ_INSTS_VALU_MUL_F32` | Vector multiply instructions, F32 |
| `SQ_INSTS_VALU_MUL_F64` | Vector multiply instructions, F64 |
| `SQ_INSTS_VALU_TRANS_F16` | Vector transcendental instructions, F16 |
| `SQ_INSTS_VALU_TRANS_F32` | Vector transcendental instructions, F32 |
| `SQ_INSTS_VALU_TRANS_F64` | Vector transcendental instructions, F64 |
| `TCC_HIT_sum` | L2 (TCC) cache hits |
| `TCC_MISS_sum` | L2 (TCC) cache misses |
| `TCP_TOTAL_CACHE_ACCESSES_sum` | L1 (TCP) total cache accesses |

| `TCP_TCC_WRITE_REQ_sum` | L1→L2 write requests (L1 misses, write) |

> `SQ_INSTS_VALU_MFMA_MOPS_F6F4` — the FP8 / FP6 / FP4 MFMA datapaths are CDNA 3
> (MI300X) only. Do not include those terms in MI250X FLOPS.

### Derived Metrics over Time (PromQL via `query`)

Hardware-counter–derived metrics over time are computed with PromQL through the
`query` subcommand (**TSDB-only** — CSV exports have no PromQL engine). Two kinds of
placeholder appear in the expressions below:

- `$job` (and `$jobstep`) are **auto-substituted** by `query` (`$job` →
  `jobid="<JOBID>"`), so `rmsjob_info{$job}` resolves the job's nodes. Leave them as-is.
- `<RATE_WINDOW>` is **not** substituted — replace it yourself with a concrete
  duration before running. Size it to ~4–6× the job's **counter** sampling interval,
  with a hard floor of 2× (PromQL `rate()` / the FLOPS subquery need at least two
  samples in the window). Hardware counters are frequently sampled **well under 1 s**,
  so the right window is usually a few seconds or less (e.g. `2s`, `500ms`) — *not*
  minutes. A minutes-wide window over sub-second samples over-smooths and erases the
  temporal detail the over-time view exists to show. Set `--step` to a similar value
  to control output resolution.

```bash
omnistat-inspect --tsdb-url $URL job <ID> query --promql '<expression below>'
```

#### FLOPS

Per-precision contributions (MI250X precisions only — vector F16/F32/F64, matrix
F16/BF16/F32/F64; **no F8/F6F4**):

```
Vector FLOPS = 64  * (ADD + MUL + TRANS + 2*FMA)    — per precision (F16, F32, F64)
Matrix FLOPS = 512 * MFMA_MOPS                       — per precision (F16, BF16, F32, F64)
Total FLOPS  = sum of vector + matrix across all precisions
```

The 64 multiplier is the wavefront width (64 work items per VALU instruction); 512
is the operations per MFMA instruction; FMA counts as 2 FLOPS.

**Per-GPU FLOP/s, averaged by node** (`avg by(instance)`):

```
rate((
  64 * (
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_ADD_F16"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MUL_F16"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_TRANS_F16"} * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_FMA_F16"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) * 2 +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_ADD_F32"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MUL_F32"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_TRANS_F32"} * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_FMA_F32"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) * 2 +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_ADD_F64"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MUL_F64"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_TRANS_F64"} * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_FMA_F64"}   * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) * 2
  ) +
  512 * (
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MFMA_MOPS_F16"}  * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MFMA_MOPS_BF16"} * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MFMA_MOPS_F32"}  * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
    (avg by(instance) (omnistat_hardware_counter{name="SQ_INSTS_VALU_MFMA_MOPS_F64"}  * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job}))
  )
)[<RATE_WINDOW>:]) != 0
```

**Job-total FLOP/s across sampled GPUs** — replace each `avg by(instance) (… )` with
`sum (rate(… )[<RATE_WINDOW>])` (or wrap the whole per-GPU expression in `sum(...)`); the
single summed series is the job's aggregate compute rate.

**% of peak:** divide a card's FLOP/s by the per-GCD matrix peak. For `bf16`/matrix
the per-GCD peak is **191.5 TF/s** (see "Per-GCD peaks" above); FP64 matrix is
47.9 TF/s, FP32/FP64 vector 24.0 TF/s.

#### HBM Bandwidth

`rate(FETCH_SIZE)` (read) and `rate(WRITE_SIZE)` (write) give KB/s per GPU:

```
rate(omnistat_hardware_counter{name="FETCH_SIZE"}[<RATE_WINDOW>]) * on(instance) group_left() rmsjob_info{$job}
rate(omnistat_hardware_counter{name="WRITE_SIZE"}[<RATE_WINDOW>]) * on(instance) group_left() rmsjob_info{$job}
```

(For a raw, unrated export of a single counter use
`timeseries --metric omnistat_hardware_counter --label name=FETCH_SIZE`, which also
works on CSV.)

#### L1 Cache Hit Rate (percent)

L1 (TCP) hit rate = 100 − 100 × (requests that missed L1 and went to L2) ÷ (total L1
accesses):

```
100 - 100 *
(
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCP_TCC_READ_REQ_sum"}[<RATE_WINDOW>])                * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCP_TCC_WRITE_REQ_sum"}[<RATE_WINDOW>])               * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCP_TCC_ATOMIC_WITH_RET_REQ_sum"}[<RATE_WINDOW>])     * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCP_TCC_ATOMIC_WITHOUT_RET_REQ_sum"}[<RATE_WINDOW>])  * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job}))
)
/
(
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCP_TOTAL_CACHE_ACCESSES_sum"}[<RATE_WINDOW>]) * on(instance) group_left() rmsjob_info{$job}) or 1 * group by(instance) (rmsjob_info{$job}))
)
```

#### L2 Cache Hit Rate (percent)

L2 (TCC) hit rate = 100 × hits ÷ (hits + misses):

```
100 *
(avg by(instance) (rate(omnistat_hardware_counter{name="TCC_HIT_sum"}[<RATE_WINDOW>]) * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job}))
/
(
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCC_HIT_sum"}[<RATE_WINDOW>])  * on(instance) group_left() rmsjob_info{$job}) or 0 * group by(instance) (rmsjob_info{$job})) +
  (avg by(instance) (rate(omnistat_hardware_counter{name="TCC_MISS_sum"}[<RATE_WINDOW>]) * on(instance) group_left() rmsjob_info{$job}) or 1 * group by(instance) (rmsjob_info{$job}))
)
```

### Counter Set Variability

The set of counters varies by job configuration — not all counters are always present. Additionally, counters can be **multiplexed** across GPUs: rocprofiler-sdk may collect different counter subsets on different GPUs within the same job (e.g., GPU 0 reports FETCH_SIZE while GPU 1 reports WRITE_SIZE). This means a given counter may have fewer series than the total number of GPUs. Run `omnistat-inspect ... job JOBID stats` and inspect the `hardware_counters` key (its `rows[].num_series` and `flops[]`) to discover which counters are present for a given job.
