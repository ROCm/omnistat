# AMD Instinct MI300X

GPU architecture profile for the AMD Instinct MI300X accelerator (CDNA 3).

## Detection Signals

This profile applies when the `type` label of `rocm_version_info` contains `MI300` (e.g., `"Instinct MI300X"`). In the `omnistat-inspect` report card this surfaces as `overview.gpu_arch` containing `mi300x`.

## Peak Theoretical Performance (per OAM, dense)

| Data Type | Vector | Matrix |
|-----------|--------|--------|
| FP64 | 81.7 TFLOPS | 163.4 TFLOPS |
| FP32 | 163.4 TFLOPS | 163.4 TFLOPS |
| TF32 | — | 653.7 TFLOPS |
| FP16 | — | 1307.4 TFLOPS |
| BF16 | — | 1307.4 TFLOPS |
| FP8 | — | 2614.9 TFLOPS |
| INT8 | — | 2614.9 TOPS |

Measured at 2100 MHz peak boost clock. The FP16/BF16/FP8/INT8 matrix figures **double** when structured sparsity is applied. TDP: 750W. Memory bandwidth: ~5.3 TB/s.

Unlike the MI250X, **one OAM is a single GPU device** (one Omnistat "card") in the default SPX partition mode, so these per-OAM figures are also the per-card figures — no division by 2.

## Multi-Die Architecture

The MI300X is a multi-chiplet module built from 8 XCDs (eXascale Compute Dies) and 4 IODs stacked over HBM3, all presented as a **single GPU device** per OAM in the default SPX (single-partition) mode. A node with 8 MI300X OAMs therefore has 8 GPU cards (cards 0-7), and **each card is a complete accelerator** — there is no GCD-pairing as on MI250X.

(In CPX mode the package can be partitioned into up to 8 logical devices, but the default and most common deployment is SPX = one card per OAM. If a node reports far more cards than physical OAMs, suspect CPX partitioning.)

## Power Reporting

**Every card reports its own power** via `rocm_average_socket_power_watts`. There is **no even/odd 0W quirk** like the MI250X — because each card is a full single-die-presented OAM rather than one of two GCDs, all cards report non-zero power. Consequently the Power variance breakdown carries the full GPU count (e.g. `n=512` on a 64-node job), not half.

## Thermal Limits

AMD does **not** publish fixed junction/throttle temperatures for the MI300X in its
public data sheets. The actual slowdown (throttle) and shutdown limits are programmed
in firmware and **vary by VBIOS/firmware revision and individual board**, so they are
not authoritative as hard-coded constants. Always read the real limits at runtime and
treat the device-reported values as authoritative for that specific node:

- `amd-smi static --limit` (per-sensor slowdown/shutdown thresholds)
- `rocm-smi --showtemp`
- the `temp*_crit` / `temp*_emergency` files under `/sys/class/drm/card*/device/hwmon/`

As a rough orientation (confirm against the device — do not rely on these numbers):
- The **edge** sensor is typically **not reported** on MI300X (`amd-smi` shows `N/A`);
  the hotspot (junction) and VRAM sensors carry the limits.
- Hotspot (junction) slowdown/shutdown limits sit around the **~100–110 °C** range.
- Unlike the MI250X, the **VRAM/HBM3** limit is **higher** than the hotspot limit, so
  on MI300X the compute die (hotspot) is usually the first sensor to reach its slowdown
  point rather than memory. Do not assume the MI250X ordering carries over.

Mapping to Omnistat metrics:
- `rocm_temperature_celsius` reflects the compute-die temperature (since edge is `N/A`
  on MI300X, this tracks the hotspot/junction reading).
- `rocm_temperature_memory_celsius` is the **VRAM/HBM3** sensor.

Interpreting telemetry against the runtime-read limits:
- **Normal**: compute-die and VRAM comfortably below their respective slowdown limits.
- **Elevated**: sustained readings approaching the slowdown limit -- check airflow,
  adjacent nodes, ambient/inlet temperature (Supermicro/Lenovo MI300X chassis are
  rated for a 10–35 °C inlet range).
- **Throttling**: when a sensor reaches its firmware slowdown threshold the GPU reduces
  clocks (SCLK) to protect itself; correlate with a drop in `rocm_sclk_clock_mhz`.
- **Shutdown**: at the shutdown threshold the device powers off to prevent damage.

Beyond the absolute thresholds, flag cards running materially hotter than their peers —
a relative outlier is often the earliest sign of a cooling problem before any limit is reached.

## Memory (HBM3)

- **Capacity**: 192 GB per OAM (single device)
- **Bandwidth**: ~5.3 TB/s peak per OAM
- **MCLK**: HBM3; no dynamic memory clock scaling exposed for scheduling decisions

## DVFS (Dynamic Voltage and Frequency Scaling)

MI300X GPUs dynamically adjust core clock speed (SCLK) based on workload:
- Active compute: clocks ramp to boost frequency (up to ~2100 MHz)
- Idle/low utilization: clocks reduce to save power

This means lower mean clocks and lower mean power are **consequences** of lower utilization, not independent problems (see "Consequence Chains" in the main SKILL.md).

## RAS Error Blocks

RAS error counters on MI300X (CDNA 3) are organized by hardware block:

| Block | Component | Notes |
|-------|-----------|-------|
| `umc` | Unified Memory Controller | HBM memory errors |
| `gfx` | Graphics/compute engine | Compute pipeline errors |
| `sdma` | System DMA engine | Data movement errors |
| `mmhub` | Memory hub | Memory controller hub |
| `pcie_bif` | PCIe interface | Host interconnect |
| `hdp` | Host data path | Host-GPU data path |
| `xgmi_wafl` | xGMI/WAFL interconnect | GPU-to-GPU (inter-die and inter-package) |

## Hardware Counters (rocprofiler-sdk)

Hardware counters are collected via rocprofiler-sdk. Values are cumulative session totals — use delta (last - first) to measure work done during a job.

### Common Counter Names

| Counter | Description |
|---------|-------------|
| `FETCH_SIZE` | HBM read (KB) |
| `WRITE_SIZE` | HBM write (KB) |
| `SQ_INSTS_VALU_MFMA_MOPS_BF16` | Matrix (MFMA) operations, BF16 |
| `SQ_INSTS_VALU_MFMA_MOPS_F16` | Matrix (MFMA) operations, F16 |
| `SQ_INSTS_VALU_MFMA_MOPS_F32` | Matrix (MFMA) operations, F32 |
| `SQ_INSTS_VALU_MFMA_MOPS_F64` | Matrix (MFMA) operations, F64 |
| `SQ_INSTS_VALU_MFMA_MOPS_F8` | Matrix (MFMA) operations, FP8 (CDNA 3) |
| `SQ_INSTS_VALU_ADD_F16` | Vector add instructions, F16 |
| `SQ_INSTS_VALU_ADD_F32` | Vector add instructions, F32 |
| `SQ_INSTS_VALU_ADD_F64` | Vector add instructions, F64 |
| `SQ_INSTS_VALU_FMA_F16` | Vector fused multiply-add instructions, F16 |
| `SQ_INSTS_VALU_FMA_F32` | Vector fused multiply-add instructions, F32 |
| `SQ_INSTS_VALU_FMA_F64` | Vector fused multiply-add instructions, F64 |
| `SQ_INSTS_VALU_MUL_F16` | Vector multiply instructions, F16 |
| `SQ_INSTS_VALU_MUL_F32` | Vector multiply instructions, F32 |
| `SQ_INSTS_VALU_MUL_F64` | Vector multiply instructions, F64 |
| `SQ_INSTS_VALU_TRANS_F16` | Vector transcendental instructions, F16 |
| `SQ_INSTS_VALU_TRANS_F32` | Vector transcendental instructions, F32 |
| `SQ_INSTS_VALU_TRANS_F64` | Vector transcendental instructions, F64 |

### FLOPS Formulas

```
Vector FLOPS = 64 * (ADD + MUL + TRANS + FMA*2)    — per precision (F16, F32, F64)
Matrix FLOPS = 512 * MFMA_MOPS                     — per precision (BF16, F16, F32, F64, F8, F6F4)
Total FLOPS  = sum of vector + matrix across all precisions
```

The 64 multiplier is the wavefront width (64 work items per VALU instruction). The 512 multiplier is the number of operations per MFMA instruction. FMA counts as 2 FLOPS (multiply + add).

### HBM Bandwidth

`rate(FETCH_SIZE)` and `rate(WRITE_SIZE)` give KB/s per GPU.

On MI300X, `FETCH_SIZE` (read) and `WRITE_SIZE` (write) **cannot be collected
simultaneously** on the same GPU — the hardware exposes only one at a time, so a job
will report either read **or** write bandwidth per GPU, or have the two multiplexed
across different GPUs (e.g. some GPUs report `FETCH_SIZE`, others `WRITE_SIZE`). Do not
expect both counters present for the same GPU, and do not sum them into a single
read+write bandwidth figure per GPU. Check `hardware_counters` `rows[].num_series` to
see which counter landed on which GPUs before interpreting bandwidth.

### Counter Set Variability

The set of counters varies by job configuration — not all counters are always present. Additionally, counters can be **multiplexed** across GPUs: rocprofiler-sdk may collect different counter subsets on different GPUs within the same job (e.g., GPU 0 reports FETCH_SIZE while GPU 1 reports WRITE_SIZE). This means a given counter may have fewer series than the total number of GPUs. Run `omnistat-inspect ... job JOBID stats` and inspect the `hardware_counters` key (its `rows[].num_series` and `flops[]`) to discover which counters are present for a given job.
